## 🚀 Why This GA Scope is Right

**1\. Summit Announcement Value**

- "MaaS GA" \>\> "MaaS TP" for keynote/field messaging  
- Jeff's point: GA announcement "much stronger"  
- Competitive positioning vs LiteLLM/Kong

**2\. LiteLLM Parity \- Mostly Achieved** With this GA scope, we match LiteLLM on:

- ✅ Token-based rate limiting  
- ✅ User/tier management  
- ✅ Usage tracking for showback  
- ✅ Enterprise OIDC support (via OCP \- validate)  
- ✅ Admin UI (LiteLLM has this)  
- ✅ API key self-service  
- ⚠️ Multi-provider (RISKY, high customer demand)  
- ❌ Throttling (deferred, llm-d scheduler coming)

**Note:** Multi-provider routing is LiteLLM's biggest differentiator. Deferring this is a competitive risk (see BRZ loss).

**3\. Clear Deferred Roadmap**

- Multi-provider(?), semantic routing, multi-cluster \= clear 3.5 features  
- Customers understand "GA foundation, advanced features coming"  
- Better than "TP with unclear GA timeline"

# Per Feature Reasoning

## ❌ CAN BE OUT OF SCOPE FOR GA (Cut to Accelerate)

### High Confidence \- Safe to Defer to 3.5/4.0

#### 1\. Chargeback (Automated Billing) ⏭️ **DEFER, but keep SHOWBACK**

**Critical Distinction Guillaume/Joe Made Dec 17:**

- **Showback:** Track token usage, attribute to users/teams → **MUST HAVE**  
- **Chargeback:** Translate tokens to dollars, automated invoicing → **Nice to have**

**Customer Reality Check:**

- Guillaume: "At least count tokens and attribute to people, they can do something with that"  
- Jonathan: "Tokens to dollars translation \- that's what this bullet means"  
- Team decision: "Split cost management into showback and chargeback, make showback highest priority"

**Why Safe to Defer Automated Billing:**

- No customer has asked for integrated billing system (they all have finance systems)  
- Customers need **data** for chargeback, not Red Hat billing software  
- Manual export → Finance team process is acceptable for GA  
- Price-per-token varies wildly by customer (no standard pricing)

**What MUST be in GA:**

- ✅ UsageRecord tracking per user, tier, model  
- ✅ Token consumption metrics (input \+ output)  
- ✅ Admin dashboard showing usage by team/user  
- ✅ Export capability (CSV/API) for finance team

**RECOMMENDATION:** ✅ **DEFER automated billing, KEEP showback tracking**

---

#### 2\. Semantic Routing ⏭️ **DEFER TO 3.5+**

**Current Status:** Separate workstream, have an intergration proposal.

**Customer Evidence:**

- BRZ wanted "intelligent routing" (body-based)  
- OCBC listed as "high priority" but GA mid-2026+  
- Telenor mentioned in context of guardrails, not routing

**Why Safe to Defer:**

- No GA blocker \- not a core MaaS feature

**Engineering Complexity (Dec 17):**

- Requires MaaS/Semantic Router/LlamaStack architectural resolution  
- Marked as "Dev Preview" for 3.4, not GA

**RECOMMENDATION:** ✅ **DEFER \- Mark as Dev Preview if shipped, not GA requirement**

**RECOMMENDATION:** ✅ **DEFER advanced dashboards, KEEP basic metrics \+ Admin UI**

### Medium Confidence \- Consider Deferring if Resources Tight

#### 7\. External OIDC/OAuth2 Integration ⚠️ **EVALUATE \- Might already be at MVP level**

**Technical Reality Check:**

**Current OCP Capability:**

- ✅ OpenShift already supports OIDC → K8s user mapping  
- ✅ Users from external IDP (Keycloak, Azure AD) become K8s users  
- ✅ Group membership flows from IDP to K8s groups  
- ✅ MaaS tier assignment uses K8s groups (already works)

**What Actually Needs Work:**

- ⚠️ MaaS might "just work" with existing OCP OIDC if groups map correctly  
- ⚠️ Need validation: Does Authorino work with OCP OIDC users out of box?

**Customer Evidence:**

- BRZ, OCBC, Telenor all listed "external OIDC" as requirement  
- BUT: They may be satisfied with existing OCP OIDC integration  
- Question: Did they specifically ask for NEW MaaS OIDC work, or just "works with our IDP"?

**Jonathan (Dec 17 transcript):**

"Deep integration with external IDPs is critical for going GA. Many customers do not want their entire organization to have OpenShift accounts."

**Counter-Point:**

- If OCP OIDC already creates K8s users from IDP → they DO have "OpenShift accounts" (just auto-created)  
- Real question: Is auto-created K8s user acceptable, or do they need MaaS to work WITHOUT K8s user creation?

**Why Might Be Deferrable:**

- If OCP OIDC → K8s users → K8s groups → MaaS tiers already works  
- May just be documentation task, not development work

**Why Might Still Be Required:**

- If MaaS API needs separate OIDC validation (not just K8s RBAC)  
- If customers have complex IDP scenarios OCP doesn't handle

**RECOMMENDATION:** ⚠️ **VALIDATE \- May be documentation task, not GA blocker**

**If Already Works:** Move to "nice-to-have documentation" and remove from resource requirements  
**If Needs Work:** Keep as GA blocker with proper scoping

#### 8\. Resilient Data Layer (PostgreSQL Backend) ⚠️ **EVALUATE**

**Current Scope:** 3.4 feature for chargeback/usage data

**Technical Need:**

- Replace Prometheus for usage tracking (performance \+ data loss issues)  
- Enable per-API-key tracking (Prometheus limitation)  
- Scalable backend for billing-grade accuracy

**Customer Impact:**

- ⚠️ Per-key tracking needed for proper chargeback  
- ⚠️ Prometheus has "lag \+ potential data loss" (Edgar's observation Oct 30\)  
- ✅ Current Prometheus sufficient for basic showback

**Engineering Dependency:**

- Requires database support (Postgres already planned for MLflow, AIPC, etc.)  
- Miriam mentioned standardizing on Postgres across platform

**RECOMMENDATION:** ⚠️ **EVALUATE \- Needed for proper showback, but Phase 2 if resources tight**

**Alternative:** Ship GA with Prometheus-based showback, document known limitations, roadmap DB backend for 3.5

## 🚨 CANNOT BE OUT OF SCOPE (GA Blockers)

### 1\. Showback / Usage Tracking 🔴 **ABSOLUTE MUST**

**Why This is Non-Negotiable:**

**Guillaume (Dec 17):**

"Chargeback/showback is the single most critical feature customers seek in MaaS."

**Customer Evidence:**

- 9 French customers: \#1 requirement across all  
- Government of Monaco: Will build custom gateway without it  
- Crédit Agricole: Need multi-entity billing  
- Safran: Fine-grained consumption tracking  
- Telenor: B2B monetization showstopper

**Minimum Showback for GA:**

- ✅ Track tokens consumed per user, subscription, model  
- ✅ Admin dashboard showing usage  
- ✅ Export capability (API/CSV) for finance teams  
- ❌ Automated billing (deferred)  
- ❌ Token-to-dollars conversion (customers do this)

---

### 2\. Operator Integration 🔴 **ABSOLUTE MUST**

**Why This is Non-Negotiable:**

**Current State:**

- 3.0: Manual shell script installation  
- 3.3: Operator integration planned

**Why Manual Install Blocks GA:**

- No upgrade path (customers stuck on version they installed)  
- No GitOps integration (requires operator CRDs)  
- Not "enterprise-ready" without operator  
- Field confusion: "Is this supported?"

---

### 3\. Subscription Model Redesign 🟡 **PROBABLY MUST**

**Current Problem (Dec 17 transcript):**

**Jonathan:**

"We have a very limited subscription model. Anyone who has interacted with MaaS will tell you how bad it is."

**What's Wrong:**

- Current model "bad" (Jonathan's own assessment)  
- Entitlements as opaque JSON (not structured)  
- No clear tier → user → model relationship

**Why This Might Be GA Blocker:**

- If current model "bad," customers will perceive GA as rushed  
- Tier management is core MaaS value prop  
- Subscription complexity affects Admin UI design

**Engineering Estimate:**

- "Just work that needs to get done" (Jonathan, Dec 17\)  
- Not architecturally complex, just cleanup

**RECOMMENDATION:** 🟡 **EVALUATE \- Probably needed for "good GA" vs "minimal GA"**

**Option A (Ideal):** Redesign for 3.4 GA  
**Option B (Fallback):** Document current model limitations, redesign for 3.5

---

### 4\. Basic Admin UI (Form-Based Tier Management) 🔴 **ABSOLUTE MUST**

**Why This is Non-Negotiable:**

**Guillaume (Nov 24):**

"Clean install of 3.0 took Kai team a full week due to new configuration items... jumping through hoops."

**Current State:**

- 3.0 DP: CLI only (kubectl \+ ConfigMap editing)  
- 3.3: Admin UI targeted (RHOAISTRAT-638)

**Customer Expectation:**

- All enterprise customers expect UI for tier management  
- LiteLLM has Admin UI (competitive gap)  
- CLI-only \= "not enterprise-ready"

**Minimum Admin UI for GA:**

- ✅ Tier list page  
- ✅ Create tier (form-based wizard)  
- ✅ Edit tier (limits, models, groups)  
- ✅ Delete tier (with validation)  
- ✅ Usage dashboard (per tier/user)  
- ❌ Create from YAML (post-GA)  
- ❌ Advanced analytics (post-GA)

**Resource Requirements:**

- UI: Dashboard team  
- Backend: Admin API endpoints (tier CRUD, usage queries)  
- UX: Andy Braren design (already in progress per Nov refinement)

**RECOMMENDATION:** 🔴 **CANNOT DEFER \- Scope down to MVP, but must ship**

---

### 5\. API Key Self-Service (Developer Experience) 🔴 **ABSOLUTE MUST**

**Customer Pattern:**

- Every customer expects self-service key generation  
- GitHub/OpenAI pattern: Create key, view once, copy  
- Developers need multiple keys (dev, staging, prod)

**Minimum Key Management for GA:**

- ✅ Create API key (select tier, get token once)  
- ✅ List my keys (name, tier, creation date, status)  
- ✅ Delete key  
- ✅ Copy token on creation (one-time display)
