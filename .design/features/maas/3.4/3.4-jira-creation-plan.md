# Epic 1: MaaS Subscription Model IA & Quota UX

## Epic Details

```
Summary: [RHOAIUX] MaaS Subscription Model IA & Quota UX

h3. Problem statement
*Label: problem-statement-data-driven*

Platform admins and AI engineers struggle to understand the relationship between Tiers, Subscriptions, Policies, and API Keys in the current MaaS architecture. Data from the Dec 2025 MaaS Worksheet and customer field feedback (9 French customers, Ethan Group, Phoenix) shows confusion around entity relationships, RBAC, and quota allocation. This impacts the ability to confidently configure MaaS and creates barriers to adoption.

h3. Objective
Define a clear, Subscription-centric information architecture for MaaS 3.4 that aligns with the PRD and resolves risky assumptions identified in 3.2/3.3. Deliverables include updated journey maps, entity relationship diagrams, and competitor UX analysis.

h3. Job stories
* When I am a Platform Admin setting up MaaS, I want to understand how Subscriptions, Tiers, and Policies relate to each other so that I can configure access and quotas correctly.
* When I am an AI Engineer creating API keys, I want to know which Subscription I'm bound to so that I understand my quota limits.

h3. Stakeholders
* PM: Jonathan Zarecki
* Eng: Jamie Land, Roy Nissim, Andrew Ballantyne, Edgar Hernandez
* UX: Andy Braren, Celestine Tan

h3. Definition of Done
* Final outcome of this epic has been reviewed by stakeholders
* A link to final designs is included in a comment on this epic and necessary stakeholders have been mentioned.
* Any updates made during review have been shared with all stakeholders so that stakeholders are aware of final changes.
* Entity relationship diagram clearly shows Model → Subscription → APIKey → User flow
* All children tasks or stories in this epic have been closed or moved to a follow-up epic.
```

# Epic 3: API Key Management UX

## Epic Details

```
Summary: [RHOAIUX] API Key Management UX

h3. Problem statement
*Label: problem-statement-data-driven*

AI Engineers need a safe, self-service experience for creating and managing API keys, but the current experience lacks key capabilities. Research from Dec 2025 UI studies (Datavant, Playtika, Martic) identified needs for: single-key CRUD, display names, descriptions, disable/enable, date last invoked, and admin revocation. h3. Objective
Deliver a complete API key management experience that supports multi-subscription scenarios, provides observability per key, and follows LiteLLM/GitHub API key patterns for familiarity.

h3. Job stories
* When I am an AI Engineer, I want to create API keys with meaningful names and descriptions so that I can organize keys by purpose.
* When I am an AI Engineer, I want to see when my key was last used so that I can identify inactive keys for cleanup.
* When I am a Platform Admin, I want to revoke API keys on behalf of users so that I can respond to security incidents.

```
Summary: [RHOAIUX] AI Asset Endpoints & Model Serving Integration with MaaS

h3. Problem statement
*Label: problem-statement-assumption*

We assume that AI Engineers experience confusion when navigating between project-scoped model deployments and MaaS-available models. This assumption is based on the current separate treatment of these concepts and the two-step promotion workflow (deploy model → flag as MaaS-compatible → admin associates with Tier). Without a coherent experience, users may not discover or correctly configure MaaS-available endpoints.

h3. Objective
Connect model serving, AI asset endpoints, and MaaS consumption into a coherent end-to-end experience. Improve discoverability and streamline the path from model deployment to MaaS availability.

h3. Job stories
* When I am a Model Deployer, I want to easily flag my model deployment as MaaS-compatible so that Platform Admins can make it available to consumers.
* When I am an AI Engineer, I want to see all available models (project and MaaS) in one view so that I can easily find and use endpoints.
* When I am an AI Engineer consuming a MaaS endpoint, I want to quickly access or create an API key from the endpoint details so that I can start using the model immediately.

h3. Stakeholders
