**Date:** December 21, 2025  
**Author:** Jonathan Zarecki

## TL;DR \- The Design in 60 Seconds

**What:** Token-based quota system for RHAI MaaS (like Run:AI for GPUs, but for LLM tokens)

**Three Entities:**

- **Model** \- Capacity (10K tokens/sec) \+ Cost (10 credits/1M tokens)  
- **Subscription** \- Groups get quotas (1K guaranteed, 3K burst) per model \+ monthly budget (500K credits)  
- **APIKey** \- User creates key → Bound to subscription → Uses subscription's quotas

**Core pattern:** Multi-model subscription (Google Cloud) \+ Guaranteed/over-quota fairness (Run:AI) \+ Internal credits (MoD/JetBrains/Windsurf)

**Example:**

```
granite deployed → 10,000 tokens/sec capacity
  ↓
enterprise-tier subscription → 1,000 tokens/sec guaranteed quota
  ↓
alice creates APIKey → Bound to enterprise-tier
  ↓
Request 100 tokens → Check quota (ok) → Route to model → Charge 0.001 credits
```

**GA scope:** Multi-model subs, per-model quotas, preemption, credits, cohorts, 10K+ keys  
**Post-GA:** Throttling (Cursor pattern), multi-cluster, fallbacks

---

## Problem Statement

Enterprise customers deploying AI at scale need **consumption-based quota management with SLA differentiation**.

**Key customer quote (MOD):**

"Deployment is not the problem. The real difficulty lies in everything around quotas, access control, and consumption management."

**Current gaps:**

- No clear story for token-based quota allocation across hundreds of users  
- No SLA differentiation (priority users vs best-effort users)  
- No consumption visibility in on-prem environments ("feels free" problem)  
- No chargeback/cost attribution per team or application

---

## Goals

1. **Consumption abstraction** \- Shift from GPU allocation to model consumption (tokens/sec)  
2. **SLA differentiation** \- Guaranteed quotas with over-quota borrowing (Run:AI fairness)  
3. **Efficiency maximization** \- Allow bursting when capacity available, fair preemption under contention  
4. **Transparent accounting** \- Internal credits make consumption tangible in on-prem  
5. **Unified multi-model access** \- One subscription for multiple models (AI IDE pattern)

---

## Assumptions

1. **Groups exist** \- Users already organized into department/team groups  
2. **Group membership managed** \- LDAP/AD sync or manual group management in place  
3. **Model capacity measurable** \- Can benchmark or estimate model throughput  
4. **Kubernetes-native acceptable** \- CRD-based approach fits customer environment  
5. **Soft multi-tenancy sufficient** \- Hard isolation not required (or handled via dedicated deployments)  
6. **Monthly budget cycles align** \- Credit resets on 1st of month acceptable  
7. **etcd can handle APIKeys** \- Or willingness to adopt external DB if needed

## Proposed Design

### Entity Overview

**Three core Entities:**

| CRD | Purpose | Key Fields | Pattern Source |
| :---- | :---- | :---- | :---- |
| **Model** | Define capacity & cost | `capacity.maxTokensPerSecond`, `cost.perMillionTokens` | Cluster-scoped registry |
| **Subscription** | Quota allocation & access | `models[]`, `quotaLimits`, `groups[]` | Google Cloud, Run:AI |
| **APIKey** | Authentication & tracking | `subscription`, `owner`, `token` | LiteLLM Virtual Keys |

**Relationships:**

```
User → Groups → Subscription → Models
                      ↓
                   APIKey (bound to Subscription)
                      ↓
                 MaaS Gateway → Model backends
```

**Simple example \- all CRDs together:**

```
# 1. Model (platform admin creates)
Model: granite-3.0-8b
  capacity: 10,000 tokens/sec
  cost: 10 credits/1M tokens

# 2. Subscriptions (platform admin creates, allocates quotas)
Subscription: enterprise-tier
  groups: [ml-engineering]
  models:
    - granite-3.0-8b:
        guaranteed: 1000 tokens/sec    # SLA guaranteed
        overQuota: 3000 tokens/sec     # Burst capacity
  budgetLimits: 500,000 credits/month

# Capacity planning (10 enterprise subscriptions):
#   Guaranteed: 10 × 1000 = 10,000 tokens/sec = Model capacity ✓
#   Over-quota: 10 × 3000 = 30,000 theoretical max (3× overprovisioned)
#   Actual: Over-quota only admitted when capacity available

# 3. User (already exists in ml-engineering group)
User: alice@company.com
  → Automatically has enterprise-tier access

# 4. APIKey (user creates via dashboard)
APIKey: alice-prod-app
  subscription: enterprise-tier
  token: "sk-abc123..."

# 5. Request flow
Request with sk-abc123 → granite-3.0-8b (100 tokens)
  ↓
Check: enterprise-tier quota for granite
  - Guaranteed: 950/1000 used
  - Request: 100 tokens
  - Decision: Admit as over-quota (950+100 > 1000 guaranteed, but < 3000 max)
  ↓
Route: granite-service:8000
  ↓
Meter: 100 tokens × 10 credits/1M = 0.001 credits
  ↓
Deduct: enterprise-tier budget (500,000 - 0.001 = 499,999.999)
```

## Subscription Design (Google Cloud Pattern)

**Core concept:** Multi-model subscriptions with per-model independent quotas

**Pattern sources:**

- **Multi-model access** → AI IDE pattern (Cursor, Windsurf)  
- **Per-model quotas** → Google Cloud Standard PayGo  
- **Guaranteed \+ over-quota** → Run:AI fairness  
- **Internal credits** → MoD customer requirement

---

### Minimal Example

```
apiVersion: ai.openshift.io/v1
kind: Subscription
metadata:
  name: enterprise-tier
spec:
  tier: Enterprise
  
  # Group membership
  groups:
    - ml-engineering
    - data-science
  
  # Multiple models, each with INDEPENDENT quota
  models:
    - name: granite-3.0-8b
      quotaLimits:
        guaranteed: 1000 tokens/sec      # Never preempted (Run:AI pattern)
        overQuota: 3000 tokens/sec       # Burst, preemptable (Run:AI pattern)
      creditRate: 10                     # Internal credits per 1M tokens
    
    - name: mixtral-8x7b
      quotaLimits:
        guaranteed: 1000 tokens/sec      # Independent from granite
        overQuota: 3000 tokens/sec
      creditRate: 15
    
    - name: gpt-4o-external
      quotaLimits:
        guaranteed: 200 tokens/sec       # Lower for expensive model
        overQuota: 500 tokens/sec
      creditRate: 50                     # Higher cost for external API
  
  # Subscription-level controls
  priority: Critical                     # For preemption (Run:AI pattern)
  budgetLimits:
    monthlyCredits: 500000               # Virtual currency (MoD pattern)
    alertThreshold: 80
    resetCadence: monthly
```

**That's it\!** Essential fields only \- everything else optional. See Appendix for full specification with all optional fields.

## Quota Enforcement (Run:AI Fairness Pattern)

### Guaranteed \+ Over-Quota Borrowing

**Quota tiers:**

```
Subscription quotas (per model):
  ├─ Guaranteed: SLA guaranteed, never preempted
  └─ Over-quota: Burst capacity, preemptable when guaranteed needed

Preemption order:
  BestEffort over-quota → Standard over-quota → Critical over-quota
  (Guaranteed quota NEVER preempted)
```

**Example:**

```
Model: granite-3.0-8b (10,000 tokens/sec capacity)

Current usage:
  enterprise-tier: 1000 guaranteed + 2000 over-quota = 3000
  standard-tier: 300 guaranteed + 1200 over-quota = 1500
  free-tier: 0 guaranteed + 5500 over-quota = 5500
  Total: 10,000 (saturated)

New request: standard-tier needs 500 tokens/sec guaranteed

Action:
  1. Preempt 500 tokens/sec from free-tier over-quota
  2. Admit standard-tier guaranteed request
  3. Free-tier gets HTTP 499, can retry for over-quota
```

## Request Flow

**7-step admission and metering process:**

1. **Request arrives** \- `POST /v1/chat/completions` with `Authorization: Bearer sk-abc123...`, `model: granite-3.0-8b`  
     
2. **Validate APIKey** \- Lookup `sk-abc123...` → Get Subscription (enterprise-tier), User ([alice@company.com](mailto:alice@company.com)), Group (ml-engineering)  
     
3. **Check quota** (for granite-3.0-8b specifically):  
     
   - Subscription.models\[granite\].guaranteed: 1000 tokens/sec  
   - Current usage: 950 tokens/sec across all keys in subscription  
   - This request: 100 tokens (estimated from prompt)  
   - **Decision:** Admit as over-quota (950 \+ 100 \= 1050 \> 1000 guaranteed, but \< 3000 over-quota limit)

   

4. **Route to model** \- Forward to Model.backend.endpoint (granite-service:8000)  
     
5. **Inference** \- vLLM generates tokens, streams response (actual: 120 tokens \= 100 input \+ 20 output)  
     
6. **Meter and charge**: (Can be async)  
     
   - Lookup Model.cost.perMillionTokens: 10 credits  
   - Calculate cost: 120 × (10 / 1,000,000) \= 0.0012 credits  
   - Update APIKey.status.creditsUsed \+= 0.0012  
   - Deduct from Subscription.budgetLimits.monthlyCredits: 500,000 \- 0.0012

   

7. **Return response** \- Stream tokens back to client

**Key points:** Quota per-model (granite independent of mixtral), credit rate from Model CRD, usage tracked at APIKey level, budget at Subscription level

## GA Scope (Mid 2026\)

### Core Deliverables

1. **Entity CRDs:** Model, Subscription, APIKey  
2. **Multi-model subscriptions:** Per-model independent quotas (Google Cloud pattern)  
3. **Quota enforcement:** Guaranteed \+ over-quota with priority preemption (Run:AI pattern)  
4. **API Key lifecycle:** Creation, rotation, expiration, revocation  
5. **Internal credits:** Per-model credit rates, monthly budget allocation (MoD pattern)  
6. **Subscription cohorts:** Borrowing/lending between same-priority (Kueue pattern)  
7. **Advanced UX:** Model-first selection, search/filter for 10+ subscriptions  
8. **Dashboards:** User, Subscription, Admin views  
9. **Chargeback:** Per-Subscription, per-APIKey, per-Model reports  
10. **Production scale:** 10,000+ API keys, 100+ users per subscription

### Out of Scope (Post-GA)

**Deferred features:**

- ❌ **Throttling/queueing** \- Speed-based fallback (Cursor pattern)  
  - Validated by Cursor IDE, requested by EU customers (BRZ, Monaco)  
  - Requires llm-d scheduler integration  
  - Deferred to focus on core GA delivery  
- ❌ **Multi-cluster quotas** \- Federated subscription tracking  
- ❌ **Automatic model fallback** \- Downgrade to cheaper models on exhaustion  
- ❌ **Organization entity** \- Multi-customer service provider hierarchy

## Design Decisions Summary

### ✅ CORE DECISIONS

| Decision | Choice | Pattern Source |
| :---- | :---- | :---- |
| **Subscription scope** | Group-based (not namespace) | MaaS Worksheet requirements |
| **Multi-model** | Yes, with per-model quotas | Google Cloud Standard PayGo |
| **Fairness** | Guaranteed \+ over-quota | Run:AI scheduler |
| **API Keys** | First-class CRDs | All 5 competitors (LiteLLM, Portkey, etc.) |
| **Chargeback** | Internal credits | MoD customer, JetBrains, Windsurf |
| **Error handling** | Blocking (HTTP 429\) | De-risk GA, throttling Post-GA |
| **Tier differentiation** | By quota amount, not model access | Cursor Pro/Pro+/Ultra (usage multipliers) |
| **Per-request selection** | User picks model per API call | AI IDE pattern (Cursor, Windsurf) |
| **Service accounts** | APIKey.type: personal vs service | LiteLLM Virtual Keys |
| **Credit reset** | Monthly hard reset | Simplicity, budget predictability |
| **Borrowing** | Same-priority cohorts only | Kueue cohort pattern |

### ❓ OPEN QUESTIONS

1. **Subscription cohort design** \- How to group subscriptions for borrowing?  
2. **Multi-subscription users** \- Can user be in multiple subscriptions? (Answer: Yes, API Key bound to one)  
3. **Preemption grace** \- Streaming request termination handling?  
4. **Multi-cluster** \- How do subscriptions span clusters?

# Personas

## Personas & Responsibilities

### Model Owner / Deployer

**Responsibilities:**

- Deploy model infrastructure (vLLM pods, GPU allocation)  
- Benchmark model capacity (load testing to determine maxTokensPerSecond)  
- Create **Model** CRD with observed capacity and cost  
- Monitor model performance and health  
- Scale model deployments (add/remove GPUs as needed)  
- Update Model.capacity when infrastructure changes  
- Sets model deployment as **“MaaS compatible”** so it can be picked up by admin.

**Tools:** kubectl, vLLM, benchmarking tools (GuideLLM, locust), Prometheus

**Note:** Often same person as Platform Admin, but can be separate (e.g., ML Engineer deploys, Platform Admin manages quotas)

---

### Platform Admin

**Responsibilities:**

- Create and manage **Subscription** CRDs (assign groups, set quotas, allocate budgets)  
- Monitor system-wide capacity and quota allocation  
- Validate capacity planning (sum of guaranteed ≤ model capacity)  
- Adjust subscription quotas based on usage patterns

**Additional for service providers:**

- Manage multi-customer subscriptions (shared \+ dedicated models)  
- Monitor per-customer quota consumption and billing

**Tools:** kubectl, admin dashboard, capacity planning scripts, batch APIs

---

### AI Engineer / Model Consumer

**Responsibilities:**

- Create **APIKey** CRDs via RHOAI Dashboard (self-service)  
- Choose subscription when creating key (model-first selection)  
- Rotate expired API keys (create new before revoking old)  
- Monitor personal quota usage and credit consumption  
- Use models via OpenAI-compatible API

**Tools:** RHOAI Dashboard, user dashboard (quota/credit visibility)

# User Flows & Examples

## Internal Credits (MoD Pattern)

**Why credits (MoD customer insight):**

"Makes consumption tangible in on-prem where costs feel invisible."

**How it works:**

```
Model defines rate:
  granite: 10 credits/1M tokens
  gpt-4: 50 credits/1M tokens

Request 100K granite: 100K × (10/1M) = 1 credit
Request 100K gpt-4: 100K × (50/1M) = 5 credits

Deduct from Subscription.budgetLimits.monthlyCredits
```

**Chargeback:** Reports by Subscription, Model, APIKey, or Group

**Industry validation:** JetBrains AI Credits, Windsurf, LiteLLM all use virtual currency

---

## Service Provider Pattern (Bryon Baker Field Requirements)

**Use case:** CSP serving 100 customers with shared \+ dedicated models

**Solution:**

```
shared-models-tier:       # All customers
  models: [granite, mixtral, llama]
  groups: [all-customers]

customer-a-dedicated:     # One customer only
  models: [customer-a-risk, customer-a-fraud]
  groups: [customer-a]
```

**Result:** Each customer gets 2 subscriptions (1 shared \+ 1 dedicated), scales to \~110 total for 100 customers

**Key insight:** Group membership \= subscription access (Bryon Baker, Dec 20, 2025\)

## Capacity Planning

**Per-model quota allocation:**

```
Model: granite-3.0-8b
  Deployment: 8 A100 GPUs = 10,000 tokens/sec

Subscription allocation (guaranteed):
  10 enterprise-tier subs × 1000 tokens/sec = 10,000 ✓

Oversubscription (via over-quota):
  10 enterprise-tier subs × 3000 max = 30,000 theoretical
  Actual: Only admitted when capacity available
```

**Validation:**

```
# Alert if overallocated
sum(subscriptions.guaranteed for granite) > Model.capacity
  → "Overallocated! Reduce quotas"
```

## Comparison to Industry Patterns

### Kueue/Run:AI Mapping

| Concept | Run:AI | RHAI |
| :---- | :---- | :---- |
| Resource | GPUs | Tokens/sec |
| Quota scope | Project | Subscription (group-based) |
| Guaranteed | Guaranteed GPUs | Subscription.quotaLimits.guaranteed |
| Over-quota | Over-quota GPUs | Subscription.quotaLimits.overQuota |
| Fairness | Reclaim preemption | Priority-based preemption |

**Key difference:** RHAI at consumption layer (tokens), Run:AI at infrastructure layer (GPUs).

### LiteLLM Mapping

| Concept | LiteLLM | RHAI |
| :---- | :---- | :---- |
| Team | Team (explicit members) | Subscription (group-based) |
| Virtual Key | Virtual Key | APIKey (CRD) |
| Budget | max\_budget (USD) | budgetLimits.monthlyCredits |
| Multi-model | 100+ providers, shared quota | Internal \+ external, per-model quotas |

**Key difference:** RHAI group-based (leverage OpenShift RBAC) vs explicit team membership.

## Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
| :---- | :---- | :---- | :---- |
| **etcd scaling issues** (10K+ APIKeys) | Medium | High | Load test in pilots, external DB fallback ready, cache lookups in-memory |
| **Over-quota oversubscription** (all users burst simultaneously) | Medium | Medium | Monitor burst patterns, adjust over-quota limits, add admission queue if needed |
| **Credit exhaustion UX** (users hit budget mid-month) | High | Medium | Alert at 80%, clear error messages, document add-on credit process |
| **Multi-subscription confusion** (10+ subscriptions per user) | Medium | Low | Model-first UX, smart defaults, search/filter interface |
| **External API rate limit changes** (provider reduces limits) | Low | Medium | Monitor provider headers, auto-adjust Model.capacity, alert admins |
| **Capacity overallocation** (admin error) | Medium | High | Validation webhook: sum(guaranteed) ≤ Model.capacity, admin dashboard alerts |
| **Preemption storms** (cascading preemptions) | Low | Medium | Limit preemption rate, preemption backoff logic, monitor preemption metrics |
| **Model capacity estimation wrong** (throughput lower than expected) | Medium | High | Start conservative, benchmark in production, runtime metrics auto-update |
| **Single user monopolizes subscription** (no per-user cap) | Medium | Medium | Implement perUserCredits (already in spec), monitor top consumers, admin intervention |
| **Quota gaming** (users create many subscriptions) | Low | Low | Audit subscription creation, limit subscriptions per group, platform admin approval |
| **Service provider isolation failure** (customer A sees customer B) | Low | Critical | Strict group membership validation, audit model access, namespace isolation for dedicated |
| **Throttling not available** (EU customers need graceful degradation) | High | Medium | Document blocking behavior clearly, prioritize throttling for Post-GA, llm-d scheduler integration |
